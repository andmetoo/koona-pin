Don't be afraid of makefiles

By Rosa Example · May 2, 2024

Every Go project I start ends up with the same handful of commands: build the binary, run the tests, check the formatting, and package a release. For a long time I kept them in a text file and copied them into the terminal. That works until the day you forget a flag and ship a debug build to production.

A makefile is a list of rules. Each rule has a target, the files it depends on, and the commands that produce it. Make looks at the timestamps of the files and runs only what is out of date, which is exactly what a build tool should do. Even when you do not care about timestamps, a makefile is a convenient place to keep the commands of a project, documented and versioned with the code.

The smallest useful makefile

Start with two targets. The first one is the default: running make without arguments builds the project. The second one runs the tests with the race detector, which you should be doing anyway.

build:
	go build ./...

test:
	go test -race ./...

Note the tab at the start of each command. Make insists on it, and a space instead of a tab is the most common error people meet in their first makefile. Most editors can show tabs and spaces differently, which helps.

Variables and phony targets

Targets like build and test are not files. If a file called test ever appears in the folder, make will think the target is up to date and do nothing. Declare such targets as phony so make always runs them. Variables keep repeated values in one place: the name of the binary, the version taken from git, the flags passed to the linker.

With these two features you can write a makefile that builds a versioned binary, runs the linters, and cleans the output folder. I wrote about how the version gets into the binary in the post about Go modules, and the official manual of GNU make covers everything else in more detail than you will ever need.

When not to use make

Make is not the right tool on Windows without a Unix shell, and it is not a package manager. If your project needs to download dependencies, let the language's own tools do it and call them from make. Keep the rules short, keep the commands readable, and your makefile will outlive several generations of build tools.
