Проверки запускаются локально по инструкции ниже. CI в GitHub Actions подготовлен, но запускается только вручную (см. [CI](#ci)). Пользовательская библиотека и профиль браузера не используются: нативные сценарии создают отдельные SQLite, WebView2 и Chrome-профили в `.test-data`.

## CI

Workflow `.github/workflows/ci.yml` запускается **только вручную** (Actions → CI → Run workflow) на `windows-2025`: `bun install`, `cargo test --locked` (он же перегенерирует типы IPC), `bun run check:bindings` — сгенерированные типы совпадают с закоммиченными, сборка TypeScript и Vite по свежим типам, Vitest, сборка расширения и `web-ext lint`, Playwright UI без `@visual`. Автоматический запуск на push и PR будет включён позже, ближе к выпуску.

Workflow `.github/workflows/linux.yml` — матрица Linux ([ниже](#linux)) — тоже **только вручную** (Actions → Linux → Run workflow). Задание `build` собирает release-бинарник на Debian 13, после него задание `check` повторяет `ci.yml` — Rust-тесты, сверка `src/bindings`, сборка, Vitest, `extension:lint`, Playwright UI без `@visual`; задания `distro` запускают бинарник из `build` на каждом дистрибутиве. Кеш `actions/cache`: реестр cargo и кеш пакетов Bun во всех заданиях, `src-tauri/target` — в `build` и `check`; под `act` шаги кеша пропускаются. Linux-минуты списываются без коэффициента.

Почему вручную. Репозиторий приватный, минуты Windows-раннеров списываются с коэффициентом ×2. Один прогон двух job занимал около 10 минут на job, то есть ≈ 40 списанных минут на коммит; 3 октября 2026 года четыре отладочных прогона израсходовали около 60 из 3000 минут месяца. При частых коммитах это быстро исчерпывает лимит.

Нативные проверки в CI не включены. На раннере WebView2 Runtime 153 запускает приложение, SQLite работает, но `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` не попадает в командную строку `msedgewebview2.exe`, поэтому порт отладки 9225 не открывается и Playwright не подключается. Локально (WebView2 154) переменная работает. При подключении CI можно передавать порт отладки через `additional_browser_args` окна в тестовой сборке. Также на раннере Tauri создаёт пустую папку профиля по умолчанию (тогда `%LOCALAPPDATA%\com.oddclicks.app`, теперь `app.koona.pin`); данные и профиль WebView2 при этом пишутся только в `.test-data`.

Версии берутся из репозитория: Bun — `.bun-version`, Rust — `rust-toolchain.toml`, npm-пакеты и Chromium для Playwright — `bun.lock`, crates — `Cargo.lock`.

## Локальный запуск

Нужны Bun из `.bun-version` (Node.js не нужен, [Р-61](decisions.md#р-61-bun-вместо-node-и-npm)), Rust из `rust-toolchain.toml` (rustup установит его сам), Microsoft C++ Build Tools и WebView2 Runtime.

**Быстрая проверка перед коммитом** (≈ 15–30 секунд при собранных зависимостях): Rust-тесты (перегенерируют `src/bindings`), сборка и типы по свежим типам, Vitest. Изменённые файлы в `src/bindings` коммитятся вместе с изменением Rust; `bun run check:bindings` проверяет, что ничего не забыто.

```powershell
bun run check
```

**Полная проверка** перед PR и при изменении UI, захвата, окна или хранилища. Из чистого клона:

```powershell
bun install
bun run build
bun run test
cd src-tauri
cargo test --locked
cd ..
bunx --bun playwright install chromium
bun run test:ui
bun run test:native
bun run test:host
bun run test:perf   # замер прокрутки, перед выпуском и после изменений сетки и списка
bun run test:extension
bun run test:extension:chrome   # установленный Chrome
bun run test:extension:edge     # установленный Edge
bun run extension:lint
bun run test:extension:firefox       # текущий Firefox
bun run test:extension:firefox:esr   # Firefox ESR 140
```

`test:extension`, `:chrome`, `:edge` и `test:extension:firefox` сами собирают расширение. Chrome берётся из `C:\Program Files\Google\Chrome\Application`, Edge — из `C:\Program Files (x86)\Microsoft\Edge\Application`; другой путь — в `KOONAPIN_CHROME` и `KOONAPIN_EDGE`. Каждый прогон ждёт повторной доставки по alarm, поэтому длится около двух минут. Firefox берётся из scoop: `%USERPROFILE%\scoop\apps\firefox\current` и `firefox-esr\current` (`scoop install extras/firefox extras/firefox-esr`), другой путь — в `KOONAPIN_FIREFOX`. Любой прогон заканчивается не позже чем через 10 минут.

Если после переноса папки проекта `cargo test` не находит файлы в `target\...\tauri-*\out`, выполните `cargo clean -p tauri --manifest-path src-tauri/Cargo.toml`. После замены файлов в `src-tauri/icons` иконка EXE обновится только после `cargo clean -p koonapin --manifest-path src-tauri/Cargo.toml`. Переменная окружения `RUSTUP_TOOLCHAIN` переопределяет `rust-toolchain.toml`; для воспроизводимого запуска её не задавайте.

Если браузеры Playwright установлены в нестандартную папку, задайте `PLAYWRIGHT_BROWSERS_PATH`. На машине владельца Chromium из папки по умолчанию `%LOCALAPPDATA%\ms-playwright` не запускается (ошибка side-by-side, `spawn UNKNOWN` в extension smoke), та же сборка из `.cache/playwright` работает; поэтому там используется `.cache/playwright`. Для нативных тестов порт отладки WebView2 9225 должен быть свободен. Каждая проверка открывает свой канал захвата (`KOONAPIN_PIPE`) и отдельную библиотеку, но Koona Pin — один экземпляр на пользователя Windows: пока работает другой Koona Pin, тестовое приложение сразу передаёт управление ему и закрывается. Поэтому перед `test:native`, `test:host` и extension smoke закройте Koona Pin (меню в трее → «Выход»); проверки сами останавливаются с этой подсказкой, если он запущен. Приложения, которые запустил host, проверки находят по пути бинарника и `--autostart` и закрывают сами. Extension smoke регистрирует host под именем `app.koona.pin.test` в ключе браузера (`Chromium` для Chrome for Testing, `Google\Chrome`, `Microsoft\Edge`) или `Mozilla` и удаляет ключ в конце.

Браузер запускается без окна с отдельным постоянным профилем. Фирменные Chrome и Edge с версии 137 не принимают `--load-extension`, поэтому распакованное расширение во всех трёх браузерах загружается одинаково: `--enable-unsafe-extension-debugging` и CDP `Extensions.loadUnpacked` (NP-014). После перезапуска браузера расширение загружается заново с тем же ID, его хранилище и очередь сохраняются. Playwright не предоставляет нажатие на кнопку расширения в панели браузера: тестовая копия worker получает ссылку на тот же обработчик `chrome.action.onClicked`, который вызывается тестом. В поставляемом worker такого тестового доступа нет. Хранилище, lifecycle, alarms, разрешения, запросы, страница подключения и SQLite используются настоящие.

Основания: [проверка WebView2](https://playwright.dev/docs/webview2), [проверка расширений](https://playwright.dev/docs/chrome-extensions).

`test:native`, `test:perf` и `site:shots` сначала сами собирают приложение, которое проверяют (`scripts/build-test-app.mjs`): интерфейс (`bun run build`) и отладочный `src-tauri/target/debug/koonapin.exe` с встроенным интерфейсом (`cargo build --features custom-protocol`), как в выпуске. Обычный `cargo build` и `cargo test` из `bun run check` пишут тот же файл без встроенного интерфейса: такое окно открывает Vite на `localhost:1420`, и CSP в нём нет совсем — Tauri применяет его только к встроенным страницам. Нативные тесты на таком бинарнике сразу останавливаются с этим объяснением, а не падают проверкой CSP.

Чтобы повторить проверку релизного бинарника, сначала выполните `cargo build --release --features custom-protocol --locked` в `src-tauri`, затем задайте `$env:KOONAPIN_TEST_BINARY='src-tauri/target/release/koonapin.exe'` для `test:native`, `test:host` и `test:extension`; host берётся из той же папки. Скрипт Chrome smoke использует модуль `node:sqlite`, Bun его поддерживает.

Базы без личных данных для проверок хранилища ([Р-10](decisions.md#р-10-модель-данных-и-миграции), [Р-11](decisions.md#р-11-чистая-схема-1-вместо-переноса-данных)). Генератор (`src-tauri/src/test_libraries.rs`, его же используют Rust-тесты) строит их настоящими миграциями в `.test-data/libraries`; результат, включая `uid`, одинаков на любой машине: пустая, образец с кириллицей и тегами, близкие дубликаты, 10 000 и 100 000 записей, более новая схема, библиотека сборки до схемы 1, файл другой программы, повреждённые страницы, файл не SQLite.

```powershell
cargo run --example test_libraries --manifest-path src-tauri/Cargo.toml
bun scripts/open-test-libraries.mjs
```

Второй скрипт открывает каждую базу собранным `koonapin.exe` (у каждой базы свой канал захвата) и печатает, открылась ли она или показала экран ошибки с кодом, схему, `application_id`, число закладок, `quick_check` и перенесённую старую библиотеку. Результат после NP-006 (3 октября 2026 года): исправные базы, включая 100 000 записей, открываются за 0,3–0,5 с; `before-schema-1.db` переносится в `koonapin.old-*.db`, создаётся пустая схема 1; `foreign-app.db`, `newer-schema.db` и `not-a-database.db` дают экраны `DB_FOREIGN`, `DB_NEWER_SCHEMA`, `DB_NOT_DATABASE` и остаются без изменений. `corrupted-pages-v1.db` открывается, затем фоновая проверка переводит библиотеку в режим только чтения с плашкой; скрипт этого не видит, это проверяет нативный тест.

Базы `*-v1.db` строятся схемой 1, как их оставил выпуск до NP-011, поэтому их открытие проверяет и миграцию на схему 2 с построением индекса. После NP-011 (3 октября 2026 года, отладочная сборка): все исправные базы открылись и получили схему 2, `quick_check ok`; `library-10k-v1.db` — 0,6 с, `library-100k-v1.db` — 2,3 с (построение индекса один раз, остальные — около 0,5 с); `newer-schema.db` (схема 3) — экран `DB_NEWER_SCHEMA`.

## Прототип Native Messaging

Прототип NP-014 ([Р-17](decisions.md#р-17-захват-через-native-messaging)) — не тест приложения, а повторяемый эксперимент с установленными браузерами. `run.mjs` копирует host в `.test-data\native-messaging-<время>`, регистрирует его в `HKCU` для Chrome, Edge и Firefox под именем `app.koona.pin.probe`, запускает браузеры без окна с тестовым расширением и в конце удаляет ключи. Результаты — `results.json` в той же папке.

```powershell
cargo build --release --manifest-path scripts/native-messaging-probe/Cargo.toml
bun scripts/native-messaging-probe/run.mjs chrome edge firefox
```

- Терминалы и агенты часто запускают процессы внутри job-объекта, который запрещает выход из него; браузер и host наследуют этот job, и результаты о job-объектах описывают терминал, а не браузер. В таком окружении запускайте `scripts/native-messaging-probe/wmi.ps1 chrome edge firefox`: WMI создаёт процесс вне job-объекта.
- Firefox берётся из scoop (`%USERPROFILE%\scoop\apps\firefox\current`) и управляется через WebDriver BiDi с `--remote-allow-system-access`.

Время запуска приложения до готовности принять захват — `bun scripts/native-messaging-probe/app-start.mjs` на release-сборке; нужна папка `.test-data\libraries` из генератора тестовых библиотек.

| `webkitgtk`, после `build` | `debian:13` (WebKitGTK 2.54), `ubuntu:26.04` (2.52) | Интерфейс в WebKitGTK дистрибутива (NP-098, `scripts/linux/ci-webkitgtk.sh`, [ниже](#интерфейс-в-webkitgtk)): ключевые экраны 14 языков в обеих темах без обрезанных подписей, тема системы и «уменьшить движение» из `settings.ini` (X11) и из gsettings GNOME на ходу (Wayland, с порталом настроек) в самом Koona Pin; артефакт `webkitgtk-*` — снимки и `report.json` |

Скрипты заданий: `scripts/linux/ci-setup.sh` (root: пакеты `deps.sh`, Rust из `rust-toolchain.toml`, Bun из `.bun-version` (`bun.sh`), пользователь `dev`), `ci-build.sh` и `ci-check.sh` (от `dev`); в `distro` — `ci-runtime.sh` (root: библиотеки времени выполнения, без компиляторов), `ci-appimage.sh` и `ci-smoke.sh` (от `dev`). Так советует и Tauri: собирать на самой старой поддерживаемой системе и проверять этот бинарник. Разработческие пакеты `deps.sh` проверяются сборкой на Debian; на остальных дистрибутивах — только инструкция. Не root: root не замечает прав на файлы и папки, и тесты прав проходили бы не по той причине. В контейнере у WebKitGTK нет пространств имён для песочницы — запуск выключает её (`WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS`), на рабочем столе этого не нужно.

### Запуск

В клоне репозитория, где установлены Docker и `act`:

```bash
act workflow_dispatch -W .github/workflows/linux.yml
```

Образ раннера, папку артефактов (`.test-data/act-artifacts`, между `build` и `distro`) и секреты из `.env` (`--secret-file`: `KOONAPIN_FEEDBACK_URL` для сборки пакетов) `act` берёт из `.actrc`; без `.env` (`.env.example`) сборка пакетов останавливается с сообщением о `KOONAPIN_FEEDBACK_URL`. Там же `--pull=false`: `act` берёт уже скачанные образы, потому что сам скачать их не может («authentication required» — `act` подставляет сохранённый вход Docker Hub, а обычный `docker pull` работает); новые образы матрицы скачиваются заранее (`docker pull debian:13` и остальные). Одно задание — `-j check` или `-j distro`, один дистрибутив — `--matrix image:fedora:44`. Пакеты для выпуска на Windows собирает `bun run build:linux`: он запускает одно задание `build` и распаковывает его артефакт в `release/publish/linux/<версия>/` ([README](README.md#выпуск)); после ручного запуска `act` распаковку делает `bun run build:linux -- --unpack`. `act` копирует рабочую копию в контейнер, пропуская то, что в `.gitignore`, — в том числе `.git` (задания его не используют, а его копия в 1,1 ГБ, когда LFS ещё хранил все версии макетов, однажды на полчаса остановила Docker Desktop) и макеты `design/lunacy/`, поэтому копия занимает секунды; Rust и `bun install` каждый прогон заново — около минуты на дистрибутив. Контейнеры `act` делят сеть хоста, а с ней и абстрактные сокеты: Xvfb в `ci-smoke.sh` слушает только файл сокета (`-nolisten local`), иначе приложение одного контейнера попадает на X-сервер другого.

Пакеты. Задания `build` и `check` берут их из тома `koona-ci-cache` (`linux.yml` подключает его в `/var/cache/koona-ci`): скачанные `.deb` — по папке на выпуск и задание, второй прогон ничего не качает. Зеркала не выбираются и не замеряются: apt берёт источники образа. Том с нуля — `docker volume rm koona-ci-cache`.

Когда одно задание падает, `act` пишет «Job failed» и у заданий, закончившихся после него, — смотреть на шаги («Success» / «Failure»), а не на итог.

### Нативные тесты на WebKitGTK

`tests/webkit` ([Р-57](decisions.md#р-57-нативные-тесты-на-webkitgtk)) — сценарии `test:native`, которые имеют смысл на Linux, через WebDriver вместо CDP: `tauri-driver` запускает `WebKitWebDriver`, тот — приложение каждой сессии с окружением драйвера (`KOONAPIN_DATA_DIR`, `KOONAPIN_PIPE`, `TAURI_WEBVIEW_AUTOMATION=true`, которое включает автоматизацию и в release-сборке). Клиент — `tests/webkit/webdriver.mjs` на `fetch`, без npm-пакетов; элементы ищутся по роли и доступному имени, как `getByRole`. Бинарник — `/usr/bin/koonapin`, если пакет установлен, иначе `KOONAPIN_TEST_BINARY` или `src-tauri/target/debug/koonapin`; host — рядом с ним.

В матрице — шаг «Native tests on WebKitGTK» каждого задания `distro`: сначала под Xvfb, затем под Weston headless, каждый со своей шиной D-Bus и домом. Одно задание с тестами повторяется так (сначала `build`: он собирает и артефакт `tauri-driver`):

```bash
act workflow_dispatch -W .github/workflows/linux.yml -j build
act workflow_dispatch -W .github/workflows/linux.yml -j distro --matrix image:debian:13
```

На своей Linux-машине без контейнера — `WebKitWebDriver` из пакета дистрибутива (`webkitgtk-webdriver` в Ubuntu и Debian, `webkitgtk6.0` в Fedora, `webkitgtk-6.0` в Arch), `cargo install tauri-driver --version 2.1.0 --locked` (другой путь — в `KOONAPIN_TAURI_DRIVER`) и в сеансе рабочего стола (Koona Pin при этом закрыт — один экземпляр на сеанс):

```bash
bun run test:webkit
```

Каждый прогон пишет библиотеку, `driver.log` (вывод драйверов и приложения) и `last.png` (окно в конце) в `.test-data/webkit-x11-<время>` или `webkit-wayland-<время>`; `ci-webkit.sh` при падении показывает конец `driver.log` без предупреждений GTK.

8 октября 2026 года (NP-095): 5 из 5 под X11 и Wayland на Ubuntu 26.04, Debian 13, Fedora 44 и Arch — около 2 с на дисплейный сервер. Остальные сценарии `test:native` пока только на Windows; что переносится и что остаётся ручным — в Р-57.

### Чего матрица не проверяет

Контейнер — не рабочий стол: в нём нет GNOME, KDE, Hyprland, трея, автозапуска, порталов, polkit, Firefox из Snap и видеокарты. Эти пункты контракта автоматически не проверяются; их проверяет человек на настоящем рабочем столе при приёмке (NP-104). Системные манифесты пакета и область systemd, в которой host запускает приложение, проверяются Rust-тестами, а на рабочем столе — при приёмке; `scripts/open-test-libraries.mjs` на Linux не проверялся; из нативных тестов на WebKitGTK пока 5 сценариев из 23 ([ниже](#нативные-тесты-на-webkitgtk)). Extension smoke на Linux идёт в задании `check` (NP-054). WebKitWebDriver ведёт и превью в MiniBrowser — экраны всех языков, тема и движение системы ([ниже](#интерфейс-в-webkitgtk), NP-098). Дробный масштаб, IME (IBus, Fcitx 5), видеокарта и рендерер DMABUF контейнер не видит — NP-111.

Разобрано при подготовке (7 октября 2026 года): из 239 Rust-тестов на Linux падал один — `a_failed_write_leaves_the_old_file_and_no_temporary_one`. На Unix переименование заменяет файл «только для чтения», запрет даёт папка без права записи — тест проверяет на Unix её. Тогда же `problem_of` перестал сравнивать коды ошибок Windows на других ОС: на Linux 39 — это `ENOTEMPTY`, и отказ назывался бы «Диск заполнен».

Виртуальные машины QEMU/KVM с автоматической установкой GNOME, KDE и Hyprland пробовались 7 октября 2026 года и отвергнуты владельцем: долго и сложно для пользы, которую дают.

### Интерфейс в WebKitGTK

NP-098, [Р-58](decisions.md#р-58-интерфейс-в-webkitgtk). У WebKitGTK нет CDP, поэтому Playwright его не ведёт. `scripts/webkitgtk-check.mjs` управляет им по WebDriver — несколько HTTP-запросов W3C, без клиентской библиотеки:

- **MiniBrowser** дистрибутива (пакет `libwebkit2gtk-4.1-0`, тот же движок, что у приложения) с превью в браузере — демо-библиотека, как у Playwright UI. Ключевые экраны (сетка, список, выделение, «Добавить ссылку», разбор, настройки) всех 14 языков при 800×550 и 1600×800, светлая тема — везде, тёмная — при 1600×800 и в английском: подписи интерфейса не обрезаны по правилу `@languages` ([languages.spec.ts](../tests/ui/languages.spec.ts)), тема действительно применилась. Снимки en, ru, de, sr, ja, ko, zh-CN — для сравнения с Windows. Прокрутка по 120 px за кадр при 1440×900, как `scroll-bench.mjs`: 10 000 закладок до конца, из 100 000 — первые 4 000 кадров (`--frames` ограничивает; без видеокарты 10 000 до конца — около 20 минут). Прокрутку меряют вручную (`--only scroll`): замеров скорости в матрице нет; 100 000 не помещаются в 5 МБ `localStorage`, их отдаёт из памяти страница скрипта (`/np098-seeded.html`), код приложения не меняется.
- **Сам Koona Pin** (`--app`, бинарник задания `build`) — так же, как его ведёт `tauri-driver`: WebKitWebDriver запускает бинарник с `TAURI_WEBVIEW_AUTOMATION=true`, своим домом и пустой библиотекой. Тема «Как в системе» и «уменьшить движение»: под X11 — из `settings.ini` GTK (его пишет KDE для программ GTK и оставляют оконные менеджеры без демона настроек), на шине без служб; под Wayland — из gsettings GNOME (`color-scheme`, `gtk-theme`, `enable-animations`), изменённых на ходу, с порталом настроек (`xdg-desktop-portal-gtk`). MiniBrowser для этого не годится: он сам выставляет `gtk-application-prefer-dark-theme`.
- **Chromium Windows** (`--chromium`, Playwright) — те же экраны и прокрутка, вторая половина пар; `--pairs <linux> <windows>` склеивает снимки двух прогонов попарно в `<linux>/pairs`.

```bash
bash scripts/linux/ci-webkitgtk.sh setup   # root: WebKitWebDriver, шрифты, Xvfb, Weston, dconf, портал, Bun, «dev»
su dev -c "bash scripts/linux/ci-webkitgtk.sh"
```

```powershell
bun scripts/webkitgtk-check.mjs --chromium
bun scripts/webkitgtk-check.mjs --pairs .test-data/webkitgtk-check/webkitgtk-2.54.0-debian-13-x11 .test-data/webkitgtk-check/chromium-win32
```

Результаты 8 октября 2026 года (Docker Desktop на рабочем ПК владельца, Xvfb и Weston без видеокарты; выводы — [Р-58](decisions.md#р-58-интерфейс-в-webkitgtk)):

- Экраны: WebKitGTK 2.54 (Debian 13) и 2.52 (Ubuntu 26.04) — 14 языков, обе темы, обрезанных подписей нет (в 2.52 — после укорочения испанского «Todos los marcadores», найденного прогоном `act`). Шрифты: Noto Sans CJK JP, KR, SC, Noto Color Emoji.
- Тема и движение в самом Koona Pin: `settings.ini` (X11, без портала) — 4 из 4; gsettings GNOME под Wayland с порталом, на ходу — 5 из 5; без портала тёмный стиль GNOME не доходит.
- Окно (`distro`, бинарник NP-055 в Debian 13): X11 — 1 цвет до запуска, 2 584 с окном; Wayland (kiosk) — 1 и 2 589.
- Полный прогон `linux.yml` через `act` — задания `webkitgtk` на обоих образах.

Результаты — `.test-data/webkitgtk-check/<движок-версия-система-сеанс>/`: `report.json`, `screens/`, `pairs/`. Параметры: `--only screens,scroll,media,gnome`, `--languages en,ja`, `--counts 10000`. WebDriver пакетом: `webkit2gtk-driver` в Debian, `webkitgtk-webdriver` в Ubuntu 26.04; версию WebKitGTK скрипт берёт у пакетного менеджера (у WebKitWebDriver нет `--version`).

## Визуальные эталоны

Эталоны находятся в `tests/ui/visual.spec.ts-snapshots` и проверяются через `toHaveScreenshot` **только локально**. Они зависят от сглаживания шрифтов конкретной машины: 3 октября 2026 года эталоны от 2 октября не совпали на той же машине (около 1 % пикселей, только сглаживание текста), а шрифты раннера отличаются сильнее. Поэтому CI запускает UI с `--grep-invert "@visual"`.

Менять эталоны следует только после просмотра изменения (`bun run test:ui -- --grep "@visual" --update-snapshots=all`: без `=all` Playwright переписывает только эталоны с отличием выше порога). Эталоны итерации 1 созданы в NP-010, пересняты в NP-012 (сетка и список по кадрам) в NP-021 (плашка и бейдж «Входящих»: в демо две закладки ждут разбора) в NP-022 (пункт «Корзина» в боковой панели стал активным) и в NP-085 (интерфейс по умолчанию на английском), сверены с кадрами 01, 02, 06, 07, 16. Тест фиксирует дату 3 октября 2026 года: от неё зависят группы списка и короткие даты.

## Ручная приёмка перед распространением

Автотесты не заменяют следующие проверки на пользовательском окружении:

- Масштаб Windows 100% и 125%, перенос окна между мониторами с разным DPI. Настоящий WebView2 в текущем окружении проверен при 150%; браузерные размеры проверены отдельно.
- Нажатие закреплённого значка расширения и ручные действия с контекстным меню трея: протоколы для [Chrome и Edge](#ручной-протокол-кнопки-в-chrome-и-edge) и [Firefox](#ручной-протокол-кнопки-в-firefox). Обработчик захвата и скрытие/открытие приложения проверены автоматически.
- Релизный установщик — [протокол ниже](#установщик), на чистой машине владельца; обновление ранее установленной версии — NP-038.

## Установщик

Протокол установки на чистой Windows 11 x64 (NP-037). Dev-сервер и отдельно запущенный EXE исправность установщика не доказывают. Машина — без Bun, Node.js, Rust и сборок Koona Pin; пользователь без прав администратора (стандартная учётная запись) для шагов 1–9. Установщик собирается `bun run build:installer` (без подписи, только для тестовой машины — результат в `release/test/windows/<версия>/`; подписанный — `bun run build:installer -- --sign`, сертификат NP-042) и переносится на машину вместе с расширениями: подписанным XPI из `release/publish/firefox/` и пакетом с ID каталога Chrome из `release/test/chrome-edge/<версия>/` (распаковать; собирается `bun run extension:build` с `CHROME_STORE_PUBLIC_KEY` в `.env`).
