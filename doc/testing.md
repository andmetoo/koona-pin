## CI

Workflow `.github/workflows/ci.yml` запускается **только вручную** (Actions → CI → Run workflow) на `windows-2025`: `npm ci`, `cargo test --locked` (он же перегенерирует типы IPC), `npm run check:bindings` — сгенерированные типы совпадают с закоммиченными, сборка TypeScript и Vite по свежим типам, Vitest, сборка расширения и `web-ext lint`, Playwright UI без `@visual`. Автоматический запуск на push и PR будет включён позже, ближе к выпуску.

Почему вручную. Репозиторий приватный, минуты Windows-раннеров списываются с коэффициентом ×2. Один прогон двух job занимал около 10 минут на job, то есть ≈ 40 списанных минут на коммит; 3 октября 2026 года четыре отладочных прогона израсходовали около 60 из 3000 минут месяца. При частых коммитах это быстро исчерпывает лимит.

Нативные проверки в CI не включены. На раннере WebView2 Runtime 153 запускает приложение, SQLite работает, но `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` не попадает в командную строку `msedgewebview2.exe`, поэтому порт отладки 9225 не открывается и Playwright не подключается. Локально (WebView2 154) переменная работает. При подключении CI можно передавать порт отладки через `additional_browser_args` окна в тестовой сборке. Также на раннере Tauri создаёт пустую папку профиля по умолчанию (тогда `%LOCALAPPDATA%\com.oddclicks.app`, теперь `app.netami.pin`); данные и профиль WebView2 при этом пишутся только в `.test-data`.

Версии берутся из репозитория: Node.js — `.nvmrc`, Rust — `rust-toolchain.toml`, npm-пакеты и Chromium для Playwright — `package-lock.json`, crates — `Cargo.lock`.

## Локальный запуск

Нужны Node.js из `.nvmrc`, Rust из `rust-toolchain.toml` (rustup установит его сам), Microsoft C++ Build Tools и WebView2 Runtime.

**Быстрая проверка перед коммитом** (≈ 15–30 секунд при собранных зависимостях): Rust-тесты (перегенерируют `src/bindings`), сборка и типы по свежим типам, Vitest. Изменённые файлы в `src/bindings` коммитятся вместе с изменением Rust; `npm run check:bindings` проверяет, что ничего не забыто.

```powershell
npm run check
```

**Полная проверка** перед PR и при изменении UI, захвата, окна или хранилища. Из чистого клона:

```powershell
npm ci
npm run build
npm test
cd src-tauri
cargo test --locked
cargo build --features custom-protocol --locked
cd ..
npx playwright install chromium
npm run test:ui
npm run test:native
npm run test:host
npm run test:perf   # замер прокрутки, перед выпуском и после изменений сетки и списка
npm run test:extension
npm run test:extension:chrome   # установленный Chrome
npm run test:extension:edge     # установленный Edge
npm run extension:lint
npm run test:extension:firefox       # текущий Firefox
npm run test:extension:firefox:esr   # Firefox ESR 140
```

`test:extension`, `:chrome`, `:edge` и `test:extension:firefox` сами собирают расширение. Chrome берётся из `C:\Program Files\Google\Chrome\Application`, Edge — из `C:\Program Files (x86)\Microsoft\Edge\Application`; другой путь — в `NETAMIPIN_CHROME` и `NETAMIPIN_EDGE`. Если `msedge.exe` перехватывает перенаправитель (отладчик IFEO, например MSEdgeRedirect), скопируйте папку `Application` Edge в `.test-data\edge-app` и укажите `NETAMIPIN_EDGE=.test-data\edge-app\msedge.exe`. Каждый прогон ждёт повторной доставки по alarm, поэтому длится около двух минут. Firefox берётся из scoop: `%USERPROFILE%\scoop\apps\firefox\current` и `firefox-esr\current` (`scoop install extras/firefox extras/firefox-esr`), другой путь — в `NETAMIPIN_FIREFOX`. Любой прогон заканчивается не позже чем через 10 минут.

Если после переноса папки проекта `cargo test` не находит файлы в `target\...\tauri-*\out`, выполните `cargo clean -p tauri --manifest-path src-tauri/Cargo.toml`. После замены файлов в `src-tauri/icons` иконка EXE обновится только после `cargo clean -p netamipin --manifest-path src-tauri/Cargo.toml`. Переменная окружения `RUSTUP_TOOLCHAIN` переопределяет `rust-toolchain.toml`; для воспроизводимого запуска её не задавайте.

Если браузеры Playwright установлены в нестандартную папку, задайте `PLAYWRIGHT_BROWSERS_PATH`. На машине владельца Chromium из папки по умолчанию `%LOCALAPPDATA%\ms-playwright` не запускается (ошибка side-by-side, `spawn UNKNOWN` в extension smoke), та же сборка из `.cache/playwright` работает; поэтому там используется `.cache/playwright`. Для нативных тестов порт отладки WebView2 9225 должен быть свободен. Каждая проверка открывает свой канал захвата (`NETAMIPIN_PIPE`) и отдельную библиотеку, но Netami Pin — один экземпляр на пользователя Windows: пока работает другой Netami Pin, тестовое приложение сразу передаёт управление ему и закрывается. Поэтому перед `test:native`, `test:host` и extension smoke закройте Netami Pin (меню в трее → «Выход»); проверки сами останавливаются с этой подсказкой, если он запущен. Приложения, которые запустил host, проверки находят по пути бинарника и `--autostart` и закрывают сами. Extension smoke регистрирует host под именем `app.netami.pin.test` в ключе браузера (`Chromium` для Chrome for Testing, `Google\Chrome`, `Microsoft\Edge`) или `Mozilla` и удаляет ключ в конце.

Браузер запускается без окна с отдельным постоянным профилем. Фирменные Chrome и Edge с версии 137 не принимают `--load-extension`, поэтому распакованное расширение во всех трёх браузерах загружается одинаково: `--enable-unsafe-extension-debugging` и CDP `Extensions.loadUnpacked` (NP-014). После перезапуска браузера расширение загружается заново с тем же ID, его хранилище и очередь сохраняются. Playwright не предоставляет нажатие на кнопку расширения в панели браузера: тестовая копия worker получает ссылку на тот же обработчик `chrome.action.onClicked`, который вызывается тестом. В поставляемом worker такого тестового доступа нет. Хранилище, lifecycle, alarms, разрешения, запросы, страница подключения и SQLite используются настоящие.

Основания: [проверка WebView2](https://playwright.dev/docs/webview2), [проверка расширений](https://playwright.dev/docs/chrome-extensions).

Чтобы повторить проверку релизного бинарника, сначала выполните `cargo build --release --features custom-protocol --locked` в `src-tauri`, затем задайте `$env:NETAMIPIN_TEST_BINARY='src-tauri/target/release/netamipin.exe'` для `test:native`, `test:host` и `test:extension`; host берётся из той же папки. Скрипт Chrome smoke использует встроенный модуль Node.js `node:sqlite`.

## Тестовые библиотеки

Базы без личных данных для проверок хранилища ([Р-10](decisions.md#р-10-модель-данных-и-миграции), [Р-11](decisions.md#р-11-чистая-схема-1-вместо-переноса-данных)). Генератор (`src-tauri/src/test_libraries.rs`, его же используют Rust-тесты) строит их настоящими миграциями в `.test-data/libraries`; результат, включая `uid`, одинаков на любой машине: пустая, образец с кириллицей и тегами, близкие дубликаты, 10 000 и 100 000 записей, более новая схема, библиотека сборки до схемы 1, файл другой программы, повреждённые страницы, файл не SQLite.

```powershell
cargo run --example test_libraries --manifest-path src-tauri/Cargo.toml
node scripts/open-test-libraries.mjs
```

Второй скрипт открывает каждую базу собранным `netamipin.exe` (у каждой базы свой канал захвата) и печатает, открылась ли она или показала экран ошибки с кодом, схему, `application_id`, число закладок, `quick_check` и перенесённую старую библиотеку. Результат после NP-006 (3 октября 2026 года): исправные базы, включая 100 000 записей, открываются за 0,3–0,5 с; `before-schema-1.db` переносится в `netamipin.old-*.db`, создаётся пустая схема 1; `foreign-app.db`, `newer-schema.db` и `not-a-database.db` дают экраны `DB_FOREIGN`, `DB_NEWER_SCHEMA`, `DB_NOT_DATABASE` и остаются без изменений. `corrupted-pages-v1.db` открывается, затем фоновая проверка переводит библиотеку в режим только чтения с плашкой; скрипт этого не видит, это проверяет нативный тест.

Базы `*-v1.db` строятся схемой 1, как их оставил выпуск до NP-011, поэтому их открытие проверяет и миграцию на схему 2 с построением индекса. После NP-011 (3 октября 2026 года, отладочная сборка): все исправные базы открылись и получили схему 2, `quick_check ok`; `library-10k-v1.db` — 0,6 с, `library-100k-v1.db` — 2,3 с (построение индекса один раз, остальные — около 0,5 с); `newer-schema.db` (схема 3) — экран `DB_NEWER_SCHEMA`.

## Замер прокрутки

Критерий NP-012: прокрутка 10 000 закладок без заметных рывков. Измеряется время между кадрами, пока список непрерывно прокручивается до конца, а страницы по 100 подгружаются по пути.

**Демо в Chromium** (`scripts/scroll-bench.mjs`): сам запускает Vite, кладёт 10 000 закладок в демо-адаптер браузера (превью — картинки и плашки), прокручивает сетку и список по 120 px за кадр (≈7 200 px/с) при окне 1440×900. Headless Chromium из Playwright рисует без GPU — это пессимистичная оценка.

```powershell
node scripts/scroll-bench.mjs
```

**Настоящий WebView2** — нативный тест «10 000 bookmarks scroll smoothly» с тегом `@perf`. В `npm run test:native` он не входит (около 35 с, зависит от загрузки машины); запуск — `npm run test:perf` перед выпуском и после изменений сетки, списка или подгрузки страниц. ## Прототип Native Messaging

Прототип NP-014 ([Р-17](decisions.md#р-17-захват-через-native-messaging)) — не тест приложения, а повторяемый эксперимент с установленными браузерами. `run.mjs` копирует host в `.test-data\native-messaging-<время>`, регистрирует его в `HKCU` для Chrome, Edge и Firefox под именем `app.netami.pin.probe`, запускает браузеры без окна с тестовым расширением и в конце удаляет ключи. Результаты — `results.json` в той же папке.

```powershell
cargo build --release --manifest-path scripts/native-messaging-probe/Cargo.toml
node scripts/native-messaging-probe/run.mjs chrome edge firefox
```

- Терминалы и агенты часто запускают процессы внутри job-объекта, который запрещает выход из него; браузер и host наследуют этот job, и результаты о job-объектах описывают терминал, а не браузер. В таком окружении запускайте `scripts/native-messaging-probe/wmi.ps1 chrome edge firefox`: WMI создаёт процесс вне job-объекта.
- Если `msedge.exe` перехватывает перенаправитель (отладчик IFEO, например MSEdgeRedirect), скопируйте папку `Application` Edge в `.test-data` и укажите путь к копии в `NETAMIPIN_PROBE_EDGE`.
- Firefox берётся из scoop (`%USERPROFILE%\scoop\apps\firefox\current`) и управляется через WebDriver BiDi с `--remote-allow-system-access`.

Время запуска приложения до готовности принять захват — `node scripts/native-messaging-probe/app-start.mjs` на release-сборке; нужна папка `.test-data\libraries` из генератора тестовых библиотек.

## Проба платформ

NP-008 ([Р-26](decisions.md#р-26-риски-других-платформ-блокеров-tauri-нет)) — эксперимент, а не тест приложения: ищет архитектурные блокеры на macOS, Linux, iOS и Android. Результаты — [матрица](release-checklist.md#эксперимент-np-008-другие-платформы).

```powershell
npm run build
pwsh scripts/platform-probe/linux/probe.ps1
pwsh scripts/platform-probe/android/probe.ps1
```

- **Linux** (Docker Desktop): сборка в Ubuntu 22.04, запуск того же бинарника в Ubuntu 22.04/24.04, Debian 12, Fedora 42 под Xvfb (`run.sh`), затем Ubuntu 24.04 без библиотеки трея (`NO_TRAY_LIB=1`) и под Wayland в Weston без экрана (`run-wayland.sh`). В контейнере у WebKitGTK нет пространств имён для песочницы: проба выключает её (`WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS`), в настоящей системе этого не нужно. Логи и скриншоты — `.test-data/platform-probe/linux/<дистрибутив>`.
- **Android** (Docker): образ с JDK 17, Android SDK и NDK (≈ 4 ГБ, лицензии Android SDK принимаются при сборке образа), APK пробного приложения и `cargo check` настоящего под `aarch64-linux-android`. Результат — `.test-data/platform-probe/android`.
- **macOS и iOS** — `.github/workflows/platform-probe.yml` на облачном macOS: `.app`, запуск со скриншотом, `cargo check` под iOS, пробное приложение под симулятор. Запускается только изменением файла workflow в ветке `research/np-008-platforms`: минуты macOS в приватном репозитории списываются ×10.
- **Пробное приложение** (`scripts/platform-probe/mobile-app`) собирается вне репозитория: Xcode и Gradle вызывают `npm run tauri` ближайшего `package.json`, внутри репозитория это было бы настоящее приложение.

## Ручная приёмка перед распространением

Автотесты не заменяют следующие проверки на пользовательском окружении:

- Масштаб Windows 100% и 125%, перенос окна между мониторами с разным DPI. Настоящий WebView2 в текущем окружении проверен при 150%; браузерные размеры проверены отдельно.
- Нажатие закреплённого значка расширения и ручные действия с контекстным меню трея: протоколы для [Chrome и Edge](#ручной-протокол-кнопки-в-chrome-и-edge) и [Firefox](#ручной-протокол-кнопки-в-firefox). Обработчик захвата и скрытие/открытие приложения проверены автоматически.
- Релизный установщик и обновление ранее установленной версии. Самостоятельные debug/release-бинарники проверены; установщик в рамках этой проверки не собирался.

Фактические скриншоты WebView2 и страницы расширения находятся в `doc/concepts`. При изменении системного масштаба или браузерного профиля результаты ручной проверки следует дописать сюда.


### Ручной протокол кнопки в Chrome и Edge

Автоматизация не нажимает кнопку на панели браузера, поэтому эту часть проверяет человек (NP-017). Нужны release-сборка приложения и собранное расширение:

```powershell
npm run build
cd src-tauri
cargo build --release --features custom-protocol --locked
cd ..
npm run extension:build
```

Release-сборка при первом запуске регистрирует host `app.netami.pin` для Chrome, Edge и Firefox (манифесты рядом с `netamipin.exe`). Приложение работает с обычной библиотекой пользователя.

| # | Действие | Ожидается |
|---|---|---|
| 1 | Запустить `src-tauri\target\release\netamipin.exe`, открыть «Настройки» → «Браузер» → «Подключить браузер» и выполнить шаги 1–2 окна дословно, не заглядывая в документацию | Расширение установлено и закреплено; записать, какой шаг потребовал догадки |
| 2 | Открыть https://example.com и нажать значок Netami Pin | Значок «✓»; ссылка во «Входящих» с источником браузера; внизу боковой панели «Браузер подключён» |
| 3 | Нажать значок ещё раз на той же странице | Значок «=», второй закладки нет |
