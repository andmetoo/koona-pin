## CI

Workflow `.github/workflows/ci.yml` запускается **только вручную** (Actions → CI → Run workflow) на `windows-2025`: `npm ci`, `cargo test --locked` (он же перегенерирует типы IPC), `npm run check:bindings` — сгенерированные типы совпадают с закоммиченными, сборка TypeScript и Vite по свежим типам, Vitest, сборка расширения и `web-ext lint`, Playwright UI без `@visual`. Автоматический запуск на push и PR будет включён позже, ближе к выпуску.

Почему вручную. Репозиторий приватный, минуты Windows-раннеров списываются с коэффициентом ×2. Один прогон двух job занимал около 10 минут на job, то есть ≈ 40 списанных минут на коммит; 3 октября 2026 года четыре отладочных прогона израсходовали около 60 из 3000 минут месяца. При частых коммитах это быстро исчерпывает лимит.

Нативные проверки в CI не включены. На раннере WebView2 Runtime 153 запускает приложение, SQLite и HTTP-сервер работают, но `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` не попадает в командную строку `msedgewebview2.exe`, поэтому порт отладки 9225 не открывается и Playwright не подключается. Локально (WebView2 154) переменная работает. При подключении CI можно передавать порт отладки через `additional_browser_args` окна в тестовой сборке. Также на раннере Tauri создаёт пустую папку профиля по умолчанию (тогда `%LOCALAPPDATA%\com.oddclicks.app`, теперь `app.netami.pin`); данные и профиль WebView2 при этом пишутся только в `.test-data`.

Версии берутся из репозитория: Node.js — `.nvmrc`, Rust — `rust-toolchain.toml`, npm-пакеты и Chromium для Playwright — `package-lock.json`, crates — `Cargo.lock`.

## Локальный запуск

Нужны Node.js из `.nvmrc`, Rust из `rust-toolchain.toml` (rustup установит его сам), Python 3, Microsoft C++ Build Tools и WebView2 Runtime.

**Быстрая проверка перед коммитом** (≈ 15–30 секунд при собранных зависимостях): Rust-тесты (перегенерируют `src/bindings`), сборка и типы по свежим типам, Vitest. Изменённые файлы в `src/bindings` коммитятся вместе с изменением Rust; `npm run check:bindings` проверяет, что ничего не забыто.

```powershell
npm run check
```

**Полная проверка** перед PR и при изменении UI, захвата, окна или хранилища. Из чистого клона:

```powershell
npm ci
npm run build
npm test
cd src-tauri
cargo test --locked
cargo build --features custom-protocol --locked
cd ..
npx playwright install chromium
npm run test:ui
npm run test:native
python scripts/smoke-native.py
npm run test:perf   # замер прокрутки, перед выпуском и после изменений сетки и списка
npm run test:extension
npm run extension:lint
npm run test:extension:firefox
```

`test:extension` и `test:extension:firefox` сами собирают расширение. Firefox берётся из `%USERPROFILE%\scoop\apps\firefox\current\firefox.exe`, другой путь — в `NETAMIPIN_FIREFOX`; приложение для этой проверки не нужно.

Если `python` открывает Microsoft Store, используйте `py scripts/smoke-native.py`. Если после переноса папки проекта `cargo test` не находит файлы в `target\...\tauri-*\out`, выполните `cargo clean -p tauri --manifest-path src-tauri/Cargo.toml`. После замены файлов в `src-tauri/icons` иконка EXE обновится только после `cargo clean -p netamipin --manifest-path src-tauri/Cargo.toml`. Переменная окружения `RUSTUP_TOOLCHAIN` переопределяет `rust-toolchain.toml`; для воспроизводимого запуска её не задавайте.

Если браузеры Playwright установлены в нестандартную папку, задайте `PLAYWRIGHT_BROWSERS_PATH`. На машине владельца Chromium из папки по умолчанию `%LOCALAPPDATA%\ms-playwright` не запускается (ошибка side-by-side, `spawn UNKNOWN` в extension smoke), та же сборка из `.cache/playwright` работает; поэтому там используется `.cache/playwright`. Для нативных тестов порты 28765 и 9225 должны быть свободны. Запускайте нативные и extension smoke последовательно: они используют один loopback-порт. Уже работающий сервер тесты не останавливают.

Chrome for Testing запускается с отдельным постоянным профилем и распакованным расширением. Playwright не предоставляет нажатие на кнопку расширения в панели браузера: тестовая копия worker получает ссылку на тот же обработчик `chrome.action.onClicked`, который вызывается тестом. В поставляемом worker такого тестового доступа нет. Хранилище, lifecycle, alarms, разрешения, запросы, страница подключения и SQLite используются настоящие.

Основания: [проверка WebView2](https://playwright.dev/docs/webview2), [проверка расширений](https://playwright.dev/docs/chrome-extensions).

Чтобы повторить проверку релизного бинарника, сначала выполните `cargo build --release --features custom-protocol --locked` в `src-tauri`, затем задайте `$env:NETAMIPIN_TEST_BINARY='src-tauri/target/release/netamipin.exe'` для `test:native` и `test:extension`. Python smoke принимает `--binary src-tauri/target/release/netamipin.exe`. Скрипт Chrome smoke использует встроенный модуль Node.js `node:sqlite`.

## Тестовые библиотеки

Базы без личных данных для проверок хранилища ([Р-10](decisions.md#р-10-модель-данных-и-миграции), [Р-11](decisions.md#р-11-чистая-схема-1-вместо-переноса-данных)). Генератор (`src-tauri/src/test_libraries.rs`, его же используют Rust-тесты) строит их настоящими миграциями в `.test-data/libraries`; результат, включая `uid`, одинаков на любой машине: пустая, образец с кириллицей и тегами, близкие дубликаты, 10 000 и 100 000 записей, более новая схема, библиотека сборки до схемы 1, файл другой программы, повреждённые страницы, файл не SQLite.

```powershell
cargo run --example test_libraries --manifest-path src-tauri/Cargo.toml
node scripts/open-test-libraries.mjs
```

Второй скрипт открывает каждую базу собранным `netamipin.exe` (порт 28765 должен быть свободен) и печатает, открылась ли она или показала экран ошибки с кодом, схему, `application_id`, число закладок, `quick_check` и перенесённую старую библиотеку. Результат после NP-006 (3 октября 2026 года): исправные базы, включая 100 000 записей, открываются за 0,3–0,5 с; `before-schema-1.db` переносится в `netamipin.old-*.db`, создаётся пустая схема 1; `foreign-app.db`, `newer-schema.db` и `not-a-database.db` дают экраны `DB_FOREIGN`, `DB_NEWER_SCHEMA`, `DB_NOT_DATABASE` и остаются без изменений. `corrupted-pages-v1.db` открывается, затем фоновая проверка переводит библиотеку в режим только чтения с плашкой; скрипт этого не видит, это проверяет нативный тест.

Базы `*-v1.db` строятся схемой 1, как их оставил выпуск до NP-011, поэтому их открытие проверяет и миграцию на схему 2 с построением индекса. После NP-011 (3 октября 2026 года, отладочная сборка): все исправные базы открылись и получили схему 2, `quick_check ok`; `library-10k-v1.db` — 0,6 с, `library-100k-v1.db` — 2,3 с (построение индекса один раз, остальные — около 0,5 с); `newer-schema.db` (схема 3) — экран `DB_NEWER_SCHEMA`.

## Замер прокрутки

Критерий NP-012: прокрутка 10 000 закладок без заметных рывков. Измеряется время между кадрами, пока список непрерывно прокручивается до конца, а страницы по 100 подгружаются по пути.

**Демо в Chromium** (`scripts/scroll-bench.mjs`): сам запускает Vite, кладёт 10 000 закладок в демо-адаптер браузера (превью — картинки и плашки), прокручивает сетку и список по 120 px за кадр (≈7 200 px/с) при окне 1440×900. Headless Chromium из Playwright рисует без GPU — это пессимистичная оценка.

```powershell
node scripts/scroll-bench.mjs
```

**Настоящий WebView2** — нативный тест «10 000 bookmarks scroll smoothly» с тегом `@perf`. В `npm run test:native` он не входит (около 35 с, зависит от загрузки машины); запуск — `npm run test:perf` перед выпуском и после изменений сетки, списка или подгрузки страниц. Тест: импорт 10 000 ссылок в чистую библиотеку, прокрутка по 400 px за кадр (быстрый рывок), страницы приходят из SQLite через IPC. ## Прототип Native Messaging

Прототип NP-014 ([Р-17](decisions.md#р-17-захват-через-native-messaging)) — не тест приложения, а повторяемый эксперимент с установленными браузерами. `run.mjs` копирует host в `.test-data\native-messaging-<время>`, регистрирует его в `HKCU` для Chrome, Edge и Firefox под именем `app.netami.pin.probe`, запускает браузеры без окна с тестовым расширением и в конце удаляет ключи. Результаты — `results.json` в той же папке.

```powershell
cargo build --release --manifest-path scripts/native-messaging-probe/Cargo.toml
node scripts/native-messaging-probe/run.mjs chrome edge firefox
```

- Терминалы и агенты часто запускают процессы внутри job-объекта, который запрещает выход из него; браузер и host наследуют этот job, и результаты о job-объектах описывают терминал, а не браузер. В таком окружении запускайте `scripts/native-messaging-probe/wmi.ps1 chrome edge firefox`: WMI создаёт процесс вне job-объекта.
- Если `msedge.exe` перехватывает перенаправитель (отладчик IFEO, например MSEdgeRedirect), скопируйте папку `Application` Edge в `.test-data` и укажите путь к копии в `NETAMIPIN_PROBE_EDGE`.
- Firefox берётся из scoop (`%USERPROFILE%\scoop\apps\firefox\current`) и управляется через WebDriver BiDi с `--remote-allow-system-access`.

Время запуска приложения до готовности принять захват — `node scripts/native-messaging-probe/app-start.mjs` на release-сборке; нужна папка `.test-data\libraries` из генератора тестовых библиотек.

## Визуальные эталоны

Эталоны находятся в `tests/ui/visual.spec.ts-snapshots` и проверяются через `toHaveScreenshot` **только локально**. Они зависят от сглаживания шрифтов конкретной машины: 3 октября 2026 года эталоны от 2 октября не совпали на той же машине (около 1 % пикселей, только сглаживание текста), а шрифты раннера отличаются сильнее. Поэтому CI запускает UI с `--grep-invert "@visual"`.

Менять эталоны следует только после просмотра изменения (`npx playwright test --grep "@visual" --update-snapshots=all`: без `=all` Playwright переписывает только эталоны с отличием выше порога). Эталоны итерации 1 созданы в NP-010 и пересняты в NP-012 (сетка и список по кадрам), сверены с кадрами 01, 02, 06, 07, 16. Тест фиксирует дату 3 октября 2026 года: от неё зависят группы списка и короткие даты.

## Ручная приёмка перед распространением

Автотесты не заменяют следующие проверки на пользовательском окружении:

- Масштаб Windows 100% и 125%, перенос окна между мониторами с разным DPI. Настоящий WebView2 в текущем окружении проверен при 150%; браузерные размеры проверены отдельно.
- Нажатие закреплённого значка расширения в обычном установленном Chrome и ручные действия с контекстным меню трея. Обработчик захвата и скрытие/открытие приложения проверены автоматически.
- Ограничения букмарклета на сайтах с CSP и политиками доступа к локальной сети.
- Релизный установщик и обновление ранее установленной версии. Самостоятельные debug/release-бинарники проверены; установщик в рамках этой проверки не собирался.

Фактические скриншоты WebView2 и страницы расширения находятся в `doc/concepts`. При изменении системного масштаба или браузерного профиля результаты ручной проверки следует дописать сюда.
