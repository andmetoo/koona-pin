# Предлагаемая дорожная карта Netami Pin

3 октября 2026 года. Это очередь для обсуждения и исполнения, не календарное обязательство. Возможности из редизайна остаются требованиями дизайна, даже если здесь предложено перенести их в следующий выпуск.

| Веха | Работа | Проверяемый результат |
| --- | --- | --- |
| M0. Границы | Аудит текущего состояния, обязательные сценарии beta, целевые ОС/архитектуры, открытые UX-решения | Одна страница объёма и список рисков |
| M1. Основа выпуска | Повтор существующих тестов, CI, пробные Linux/macOS сборки, тестовая БД, план данных/переименования | Воспроизводимая desktop-сборка, ранние ограничения известны |
| M2. Новый интерфейс | Токены и Inter, бренд, оболочка, сетка/список, темы, фокус, поиск | Пользователь работает с прежней библиотекой в новом UI |
| M3. Разбор и безопасность данных | Входящие, корзина, восстановление, JSON export/restore, затем массовые команды | Закладку можно сохранить, разобрать, удалить и вернуть после перезапуска |
| M4. Desktop-alpha | Установщики Windows/Linux/macOS, платформенные отличия, CSP и legacy API, обновление | Чистая установка и переход с прежней версии на каждой заявленной ОС |

| M6. Desktop 1.0 | Подписанные пакеты по выбранным каналам, release checklist, страница загрузки, поддержка | Проверенный публичный выпуск |
| M7. Следующие desktop-функции | Перетаскивание, дополнительные форматы, уборка, другие браузеры по спросу | Каждая функция решает наблюдаемую проблему |

Mobile-эксперимент провести ещё в M1: запуск, SQLite, сохранение через «Поделиться», оценка нативного кода. Полноценная M8 не должна незаметно расширять объём desktop-beta. Если эксперимент выявит блокер Tauri для обязательного сценария, отдельно пересмотреть мобильную оболочку.

## Ближайшие задачи

1. **NP-001: границы desktop-beta.** Выбрать обязательные функции, ОС/архитектуры и форматы пакетов. Результат: принятый scope, без изменений кода.
2. **NP-002: воспроизвести baseline.** Запустить существующие проверки на отдельной БД, записать коммит, окружение и реальные результаты. Добавить CI на выбранном хостинге.
3. **NP-003: ранние платформенные сборки.** Собрать на Linux/macOS, выписать проблемы трея, окна, путей, шрифтов и упаковки. Не объявлять поддержку до smoke-проверки пакетов.
4. **NP-004: политика старых данных.** Решить статус существующих закладок во входящих, мягкое удаление, backup/restore, совместимость старого пути OddClicks и будущего имени. Проверить миграцию на копии.
5. **NP-005: состояния ближайшего экрана.** Уточнить сетку/список и входящие, темы, ошибки, узкое окно, клавиатуру. Принять дизайн.
6. **NP-006: токены и основной экран.** Перенести новый бренд и один рабочий сценарий, сохранить действия с существующей библиотекой. Обновить эталоны после визуального просмотра.
7. **NP-007: корзина.** Мягкое удаление и восстановление одной записи, затем отдельная задача для массового сценария.
8. **NP-008: резервная копия.** Экспорт, проверка формата и восстановление в тестовой библиотеке. HTML/CSV-экспорт не называть полной резервной копией.
9. **NP-009: безопасность до beta.** CSP, токен/совместимость `/api/add`, ограничения внешних запросов и обезличенные логи.
10. **NP-010: установщик и обновление.** Чистая установка, обновление старой версии, запуск, сохранность библиотеки, удаление приложения согласно описанной политике данных.

NP-001 определяет обязательность последующих задач. NP-004 предшествует миграциям и переименованию хранилища, NP-005 предшествует реализации соответствующего UI. NP-003 можно исследовать параллельно, если доступна другая среда. Номера здесь локальные, задачи в трекере не создавались.

## Решения, которые принимает владелец

- Точные поддерживаемые версии ОС и архитектуры. «Linux» без списка проверенных окружений слишком широко.
- Нужны ли drag-and-drop и все форматы экспорта уже в beta.
- Как трактовать старые закладки при введении входящих.
- Каким будет разбор: одна карточка или список с клавиатурой.
- Какие каналы распространения и обновлений поддерживать первыми.
- Как пользователи перенесут библиотеку на телефон, и оправдан ли сервер синхронизации.

## Пример первых двух итераций

Итерация A: границы beta, повтор baseline, рискованные платформенные сборки, план миграции. Демонстрация: приложение собирается воспроизводимо, ограничения записаны.

Итерация B: один сценарий нового интерфейса и его приёмка, без одновременной полной замены всей архитектуры. Демонстрация: новая сетка работает с настоящей тестовой SQLite, обеими темами и ошибками.

Продолжительность выбирать по доступному времени. Срок следующей вехи уточнять после первой фактической итерации, а не по количеству агентов.
