# Дорожная карта Netami Pin

3 октября 2026 года. Заменяет предыдущую версию (вехи M0–M8 и локальные NP-001–NP-010, в трекере не создавались). Это очередь работы, а не календарь: сроки появятся после первых завершённых задач.

Подробности задач — в GitHub Issues; соответствие ключей `NP-xxx` и номеров — в [issues/README.md](issues/README.md). Пользовательские сценарии — в [scenarios.md](scenarios.md), обоснования — в [decisions.md](decisions.md).

## Принятые решения

Netami Pin — личная библиотека для человека, который сохраняет много ссылок и хочет быстро находить и разбирать накопленное.

- **Первый публичный выпуск — Windows-beta** со всем редизайном итерации 1.
- **Chrome, Edge и Firefox** поддерживаются в первом выпуске. Приложение распространяется установщиком; канал расширений Chrome и Edge выбирается в NP-001, Firefox — подписанный XPI без публичного листинга.
- Порядок платформ: **Windows → macOS → Linux → Android → iOS**.
- **Синхронизация — после desktop-портов, до мобильных выпусков.**
- Локальное ядро бесплатно и работает без аккаунта. Платные сервисы — позже; окончание подписки не лишает локальной библиотеки и возможности забрать данные.
- Стек сохраняется: Tauri 2, Rust, React, TypeScript; новый интерфейс — **Tailwind 4**. **SQLite — единственное хранилище**, поиск на FTS5 ([Р-2](decisions.md#р-2-sqlite-остаётся-единственным-хранилищем)).
- Офлайн-копии страниц, режим чтения, ИИ-функции, Safari, командные библиотеки и публичные коллекции в план автоматически не входят.

## Линия отсечения

Решение выпускать beta со всем редизайном принято. Чтобы необязательное не задерживало выпуск, NP-026, NP-030, NP-035 и NP-036 помечены `beta-optional`. Их отрезают, если остальная beta готова, а они нет; дизайн и требования из [redesign.md](redesign.md) при этом остаются. Окончательный список и условие отсечения — в NP-001.

## Первая рабочая очередь

**NP-001 → NP-002, NP-003, NP-004, NP-005 → NP-006, NP-007 → NP-009, NP-010, NP-011.**

NP-003 начать сразу после NP-001: подпись кода и хостинг требуют времени. NP-008 идёт после воспроизводимой сборки и не задерживает Windows без найденного архитектурного блокера.

## Как вести backlog

- **Milestone** — выпуск. **Родительская issue** — сценарий W0–W7 или будущий выпуск. **Дочерняя issue** — задача `NP-xxx` с отдельным проверяемым результатом.
- Метки: тип (`scenario`, `feature`, `decision`, `research`, `release`, `bug`), область (`design`, `library`, `capture`, `data`, `sync`, `distribution`, `infra`, `billing`), платформа (`windows`, `macos`, `linux`, `android`, `ios`), `beta-optional`.
- Доска: `Backlog → Ready → In progress → Review → Done`. Приоритет задают milestone и зависимости.
- Каждая issue содержит ситуацию и результат, текущее состояние, границы, критерии приёмки, проверки, зависимости и изменения документации. Шаблон — `.github/ISSUE_TEMPLATE/task.md`.
- В работу поступают только задачи `Ready`; по умолчанию одна задача реализации одновременно. Дизайн и контракты согласуются до зависимого кода. Общие миграции, `App.tsx` и бинарные макеты — один автор за раз.
- Проверяющий получает требования, diff и результаты тестов. Закрытие issue требует приёмки результата; выпуск отмечается отдельно.
- Ошибки, найденные при приёмке, — отдельные issues с меткой `bug` и ссылкой на задачу.
