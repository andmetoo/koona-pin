# Технические и продуктовые решения

Записи по формату из [шаблона задачи](task-template.md#запись-технического-решения). Новое решение добавляется в конец; отменённое не удаляется, а помечается ссылкой на заменившее. Решения, которые ещё предстоит принять, оформлены задачами `decision` (индекс — [issues/README.md](issues/README.md)).

## Р-1. Платформы и порядок выпусков

3 октября 2026 года.

**Контекст:** нужен первый публичный выпуск без одновременной поддержки трёх ОС и телефонов.

**Решение:** Windows → macOS → Linux → Android → iOS. Первый публичный выпуск — Windows-beta со всем редизайном итерации 1 и захватом из Chrome, Edge и Firefox. Синхронизация появляется после desktop-портов и до мобильных выпусков. Локальное ядро бесплатно и работает без аккаунта; платные сервисы (синхронизация) — позже. Офлайн-копии страниц, режим чтения и ИИ-функции вне обязательного плана.

**Последствия:** ранний эксперимент с другими платформами (NP-008) ищет только архитектурные блокеры. Мобильные сценарии опираются на синхронизацию, поэтому её проектирование предшествует Android.

**Повод пересмотреть:** блокер Tauri на mobile, обратная связь beta, которая требует телефон раньше Linux.

## Р-2. SQLite остаётся единственным хранилищем

3 октября 2026 года.

**Контекст:** возник вопрос, не заменить ли SQLite лёгкой NoSQL-базой: текущий поиск медленный, а данные нельзя терять.

**Замер.** [`scripts/search-bench`](../scripts/search-bench/src/main.rs), та же сборка SQLite 3.46 (rusqlite 0.32 bundled), синтетическая библиотека с русскими и английскими словами, медиана прогонов на рабочем ПК:

| Способ | 10 000 закладок | 100 000 закладок |
| --- | --- | --- |
| Текущий `db::get_bookmarks`: все строки, запрос тегов на каждую, подстрока в Rust | 90 мс | 2 207 мс |
| FTS5 `trigram` (подстрока), общее число + страница 100 с тегами | 2,4 мс | 28 мс |
| FTS5 `unicode61`, префикс слова | 0,9 мс | 12 мс |

Под запрос подходила почти половина записей — это худший случай; реальные запросы избирательнее. FTS5 нашёл ровно те же записи, что текущий поиск, свернул регистр кириллицы и нашёл подстроку в домене. Встроенные `LIKE` и `lower()` SQLite кириллицу не сворачивают: `'%архитект%'` нашёл 0 записей вместо 1 030. Ни один индекс не приравнял «ё» к «е».

**Варианты:**

1. Оставить SQLite, исправить запросы и добавить FTS5.
2. Встраиваемое хранилище «ключ — значение» (redb, LMDB, RocksDB). Надёжны, но полнотекстового поиска, связей, уникальности и миграций нет — всё это пришлось бы писать вручную.
3. Встраиваемая документная база. sled официально в beta без стабильного формата файла; Realm свёрнут MongoDB; SurrealDB и PoloDB молоды для роли единственного хранилища личных данных.

**Решение и причина:** вариант 1. Медленным был способ запроса, а не SQL. Данные реляционные: закладки ↔ теги, коллекции, уникальность URL, атомарные массовые действия, корзина. SQLite — проверенное хранилище с транзакциями и стабильным форматом файла, встроено в Android и iOS, на нём построены готовые решения синхронизации.

**Последствия:** NP-011 переводит выборку на FTS5 со свёрткой ё/е и выдачей страницами; NP-012 добавляет виртуализацию, потому что следующим узким местом станет отрисовка тысяч карточек.

**Проверка:** повторить замер на реальной схеме в NP-011; ориентир p95 поиска ≤ 150 мс на 10 000 записей на целевом ПК.

**Повод пересмотреть:** понадобятся поиск с опечатками, ранжирование или русская морфология. Тогда добавить Tantivy как **производный индекс**, который строится из SQLite и перестраивается при потере. Источник данных не меняется.

## Р-3. Надёжность хранилища

3 октября 2026 года.

**Контекст:** в текущем коде найдены места возможной потери или порчи данных (подробно в NP-006 и [architecture.md](architecture.md#известные-ограничения-хранилища)).

**Решение:**

- `PRAGMA synchronous = FULL` вместо `NORMAL`: подтверждённый захват переживает отключение питания. При объёме записей приложения разница в скорости незаметна.
- `busy_timeout` на соединении.
- Последовательные миграции: каждая в своей транзакции, перед каждой — копия `before-vN`.
- Отказ открывать базу с `user_version` новее поддерживаемой. Понятный экран вместо panic при ошибке открытия или миграции.
- Автоматические резервные копии с ротацией и `PRAGMA quick_check` при запуске.
- Начальные данные создаются один раз в миграции.
- Тяжёлые команды (импорт, экспорт, копии, проверка ссылок) — асинхронные, вне главного потока.

**Проверка:** тесты NP-006 на тестовых базах прежних версий, отказ записи посреди миграции, запуск старого бинарника на новой схеме.

## Р-4. Схема заранее готова к синхронизации

3 октября 2026 года.

**Решение:** протокол синхронизации, сервер и провайдера не выбирать. Но уже в первой новой миграции добавить UUID записи рядом с локальным `id`, использовать мягкое удаление (`deleted_at`) как надгробие и единый формат времени UTC. Источник сохранения (`source`) хранить с записью. Точный состав — в NP-005.

**Причина:** иначе к вехе «Синхронизация» понадобится вторая крупная миграция всех библиотек.

## Р-5. Интерфейс: React и Tailwind 4

3 октября 2026 года.

**Решение:** React 19, TypeScript и Vite сохраняются. Новый интерфейс сразу строится на Tailwind 4 (NP-010) без промежуточного переноса стилей «Редакции»: `@tailwindcss/vite`, токены гайдлайна в `@theme`, тёмная тема через `@custom-variant` по `data-theme`. `tailwind.config.js` и autoprefixer удаляются. Списки большой длины виртуализируются. TypeScript-типы IPC генерируются из Rust, ошибки команд имеют машинный код (NP-007).

**Последствия:** Tailwind 4 требует современный движок (Chrome 111+, Safari 16.4+). WebView2 обновляется сам. Для macOS это минимальная версия системы с WKWebView уровня Safari 16.4, для Linux — минимальная версия WebKitGTK. Обе проверяются в NP-008 и при выборе матрицы Linux.

## Р-6. Захват из браузера

3 октября 2026 года.

**Решение:** HTTP v1 на `127.0.0.1:28765` с токеном остаётся основой. После появления установщика исследовать Native Messaging (NP-014): он убирает ручной перенос токена, конфликт порта и позволяет приложению знать о подключённых браузерах. Решение по legacy `/api/add` и ограничениям запросов метаданных — NP-019. Firefox распространяется подписанным XPI без публичного листинга; канал Chrome и Edge в beta выбирается в NP-001.

## Р-7. Ведение backlog

3 октября 2026 года.

**Решение:** задачи живут в GitHub Issues `andmetoo/netamipin`; после публикации источник истины — GitHub, локальный индекс [issues/README.md](issues/README.md) хранит только соответствие ключей и номеров. ## Р-8. Контракт Windows-beta

3 октября 2026 года. Задача NP-001, полный текст — [roadmap.md](roadmap.md#контракт-windows-beta).

**Контекст:** до реализации нужен закрытый объём beta, чтобы исполнители не додумывали платформу, языки и границы.

**Решение:**

- Только Windows 11 x64. Бесплатные обновления безопасности Windows 10 для частных лиц заканчиваются 13 октября 2026 года, ARM64-устройства для проверки нет.
- NSIS на пользователя: установка и обновления без прав администратора, регистрация в `HKCU`. WebView2 через встроенный bootstrapper: установщик не зависит от сети, если WebView2 удалён.
- Chrome и Edge 120+, Firefox — релиз и ESR 140.
- Расширения Chrome и Edge — unlisted в каталогах: обновляются сами и не дают предупреждений режима разработчика. Стоимость — аккаунт разработчика Chrome Web Store и проверка каталогов.
- Интерфейс на английском и русском, английский — исходный и запасной язык, по умолчанию язык системы. Заменяет «язык интерфейса — русский» из [plan.md](plan.md). Документация остаётся на русском.
- Автозапуск включён по умолчанию, старт в трей: иначе ссылки из браузера ждут в очереди до ручного запуска.
- Линия отсечения: NP-026, NP-030, NP-035, NP-036, решение при старте NP-039.

**Последствия:** локализация входит в основу интерфейса (NP-010), каждая UI-задача сдаёт строки на двух языках. macOS и iOS в NP-008 проверяются только сборкой: Mac и iPhone нет.

**Повод пересмотреть:** запросы beta-пользователей на Windows 10 или ARM64; отказ каталога в unlisted-публикации.

## Р-9. Распространение Windows

3 октября 2026 года. Задача NP-003. Цены и условия проверены в тот же день.

**Контекст:** публичной beta нужны подписанный установщик, обновления и канал обратной связи. Идентификаторы нельзя менять после первого установщика, а проверка издателя занимает недели. Тип установщика задан в [Р-8](#р-8-контракт-windows-beta): NSIS на пользователя.

**Решение:**

| Вопрос | Решение | Стоимость |
| --- | --- | --- |
| Подпись кода | [Azure Artifact Signing](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart) (бывший Trusted Signing), издатель — организация, профиль Public Trust, регион West или North Europe. Подписываются EXE приложения и установщик через `bundle.windows.signCommand` | Basic $9,99 в месяц (до 5 000 подписей), нужна платная подписка Azure |
| Идентификаторы | `identifier` `app.netami.pin`, `productName` «Netami Pin», EXE `netamipin.exe` (в NP-037 закрепить через `mainBinaryName`: иначе бандлер называет EXE по `productName`), установка NSIS на пользователя в `%LOCALAPPDATA%\Netami Pin` (путь по умолчанию шаблона Tauri), данные в `%APPDATA%\Netami Pin`. Upgrade code относится к MSI и не используется. Не меняются после первого публичного установщика | — |
| Хостинг | Отдельный публичный репозиторий `andmetoo/netamipin-releases`: GitHub Releases с установщиком, расширениями и `latest.json`. Updater читает `https://github.com/andmetoo/netamipin-releases/releases/latest/download/latest.json`. Код остаётся в приватном репозитории | Бесплатно |
| Ключ подписи обновлений | `tauri signer generate` с паролем. Приватный ключ и пароль — в менеджере паролей владельца и зашифрованная офлайн-копия; в репозитории только публичный ключ. В секреты GitHub — когда появится выпуск из CI (копию оттуда прочитать нельзя) | — |
| Обратная связь | Issues в `netamipin-releases` с шаблоном отчёта; почтовый ящик на домене `netami.app`; форма на pin.netami.app (NP-040) | Бесплатно, кроме обработчика формы |

**Варианты подписи:**

1. Azure Artifact Signing — выбран. Дешевле сертификата, ключ в облачном HSM без USB-токена, подписывает из CI.
2. OV-сертификат CA (Certum, Sectigo, DigiCert) — $110–300 в год, ключ на токене или в облаке CA. Для SmartScreen равнозначен варианту 1.
3. EV-сертификат — от $400 в год. С 2024 года не обходит SmartScreen, поэтому переплата не оправдана.
4. Microsoft Store с MSIX — подпись бесплатна, но меняет формат пакета: виртуализация файловой системы, другой путь обновлений, сложнее Native Messaging (NP-014). Противоречит Р-8.
5. Без подписи — SmartScreen блокирует установку для большинства пользователей.

**Последствия:**

- Ни один способ не убирает предупреждение SmartScreen у первых выпусков: репутация копится по издателю. Страница загрузки объясняет «Подробнее → Выполнить в любом случае» до накопления репутации.
- Проверка организации: юридическое название, сайт, основной и дополнительный адреса на домене организации, регистрационный номер, адрес; документы не старше 12 месяцев; регистрация домена на организацию. Срок 1–20 рабочих дней, дольше при запросе документов. Ошибку в заявке нельзя исправить — только новая заявка.
- Потеря ключа обновлений означает, что установленные копии не примут ни одного обновления: пользователям придётся вручную скачать новую версию с новым публичным ключом. Компрометация ключа — то же самое плюс отзыв выпусков, подписанных после утечки, и объявление на странице загрузки.
- Сертификаты Artifact Signing короткоживущие и выдаются сервисом при каждой подписи; подпись снабжается отметкой времени и остаётся действительной после истечения сертификата.

**Действия владельца:**

1. Создать платную подписку Azure, зарегистрировать провайдер `Microsoft.CodeSigning`, создать Artifact Signing account (Basic).
2. Подать заявку Organization → Public, назначить себе роль Artifact Signing Identity Verifier. Записать дату подачи в NP-003.
3. После статуса Completed создать профиль Public Trust; пробно подписать тестовый EXE и проверить подпись `signtool verify /pa`.
4. Сгенерировать ключ updater и сохранить по правилу выше:

   ```powershell
   npx tauri signer generate -w "$env:USERPROFILE\.tauri\netamipin.key"
   ```

   После переноса в менеджер паролей и офлайн-копию удалить файл с диска.

**Проверка:** пробная подпись тестового EXE выбранным способом; ключ updater восстанавливается из офлайн-копии на другом компьютере.

**Повод пересмотреть:** отказ в проверке организации; рост объёма выше 5 000 подписей в месяц; решение публиковать в Microsoft Store.

## Р-10. Модель данных и миграции

3 октября 2026 года. Задача NP-005. Продуктовые правила (пункты 1, 2 и 4) выбрал владелец; остальное предложил исполнитель, принимается ревью владельцем.

> Частично заменено [Р-11](#р-11-чистая-схема-1-вместо-переноса-данных): «миграции v2» нет, состав ниже создаётся сразу как схема 1; перенос старых данных (заполнение `triaged_at`, `uid` из `created_at`, перевод времени), копирование OddClicks из пункта 8 и тестовые библиотеки v0/v1 отменены. Модель данных, правила корзины, источника, копий и проверки остаются.

**Контекст:** входящие, корзина, источник сохранения и будущая синхронизация меняют модель данных. Если ввести их разными миграциями, каждая библиотека переживёт несколько крупных перестроек. Поэтому всё ниже входит в **одну миграцию v2** (реализация — NP-006, NP-021, NP-022).

**Решение:**

1. **Входящие.** Поле `triaged_at`: `NULL` — закладка во «Входящих». Миграция v2 ставит `triaged_at = created_at` всем существующим закладкам: после обновления библиотека выглядит как раньше, «Входящие» пусты. Новые закладки из расширения, букмарклета и ручного добавления приходят неразобранными.
2. **Корзина и уникальный URL.** Одна строка на адрес: `UNIQUE(url)` остаётся и охватывает закладки в корзине. Повторное сохранение адреса из корзины расширением, букмарклетом или вручную восстанавливает её: `deleted_at = NULL`, `triaged_at = NULL` (снова во «Входящих»), заметки, теги и коллекция сохраняются, ревизия растёт. Импорт такие адреса пропускает и показывает счётчик «в корзине: N»: иначе повторный импорт закладок браузера отменил бы уборку. Повтор квитанции с тем же `request_id` возвращает прежний результат и ничего не восстанавливает.
3. **Протокол захвата.** Расширения 0.3 и старше принимают только `created` и `existing`, поэтому восстановление отвечает `outcome: "created"` с полем `restored: true`; новые версии расширения показывают «Восстановлено из корзины».
4. **Импорт HTML.** В диалоге выбор «В библиотеку» (по умолчанию, `triaged_at` = время импорта) или «Во входящие». Папка верхнего уровня становится коллекцией, вложенные папки — тегами; системные папки браузера («Панель закладок», «Другие закладки», «Мобильные») пропускаются.
5. **Источник.** `source TEXT` с `CHECK` из `app`, `chrome`, `edge`, `firefox`, `extension` (браузер не назван), `bookmarklet`, `import`. `NULL` — сохранено до v2, источник неизвестен. HTTP v1 принимает необязательное поле `source` от расширения (NP-016), `/api/add` пишет `bookmarklet`, IPC — `app`, импорт HTML — `import`, восстановление из JSON сохраняет исходное значение.
6. **Подготовка к синхронизации** ([Р-4](#р-4-схема-заранее-готова-к-синхронизации)). `uid TEXT NOT NULL UNIQUE` — UUIDv7 в нижнем регистре у закладок, коллекций и тегов; для существующих строк время UUID берётся из `created_at`, так порядок сохраняется. Локальный `id` остаётся для связей и IPC. `deleted_at` — надгробие закладки. Очистка корзины через 30 дней (NP-023) удаляет строку и пишет `(uid, kind, deleted_at, purged_at)` в таблицу `tombstones`; удаление коллекции и тега тоже оставляет запись в `tombstones`.
7. **Время.** Везде UTC в виде `YYYY-MM-DDTHH:MM:SS.sssZ`: строка сортируется так же, как время. Миграция v2 переводит старые значения: дата без времени → полночь UTC, смещение → UTC.
8. **Каталог данных** уже перенесён в NP-009: `%APPDATA%\Netami Pin`, копия OddClicks не трогается. Галочка «Удалить данные приложения» в деинсталляторе Tauri удаляет только `%APPDATA%\app.netami.pin` и `%LOCALAPPDATA%\app.netami.pin` (профиль WebView2). NP-037 добавляет хук NSIS: та же галочка с подписью «Удалить библиотеку и резервные копии» удаляет и `%APPDATA%\Netami Pin`. По умолчанию галочка снята. Папку OddClicks деинсталлятор не удаляет никогда.
9. **Резервные копии** — файлы SQLite через `VACUUM INTO` в `%APPDATA%\Netami Pin\backups`: согласованная копия с учётом WAL, сжатая, восстанавливается тем же кодом открытия базы. Автоматически при запуске и раз в сутки работы в трее, если последней копии больше 24 часов. Хранятся 7 последних ежедневных и 4 еженедельных (около 11 × 35 МБ для 100 000 закладок). Перед каждой миграцией — `netamipin.before-vN.db`, хранятся две последние. Перед восстановлением из копии или JSON — внеочередная копия. JSON-экспорт (NP-032) — переносимый формат для человека и других программ, а не механизм резервного копирования: в нём нет квитанций и настроек.
10. **Проверка целостности.** `PRAGMA quick_check` после автоматической копии в фоне, не задерживая запуск. Ошибка → плашка с предложением восстановить последнюю исправную копию.
11. **Новая схема и старый бинарник.** Миграция v2 ставит `PRAGMA application_id = 0x4E50494E` («NPIN»). При открытии: чужой `application_id` → отказ «Это не библиотека Netami Pin»; `user_version` больше поддерживаемой → экран «Библиотеку обновила более новая версия Netami Pin (схема N). Установите последнюю версию с pin.netami.app». В этом состоянии приложение ничего не пишет, не мигрирует и не запускает HTTP-сервер. Сборки со схемой v1 такой проверки не имеют, но публично не выпускались, а OddClicks работает со своей копией базы.

**Миграции: откат и что видит пользователь.** Порядок для каждой миграции vN:

| Шаг | При ошибке | Пользователь видит |
| --- | --- | --- |
| `VACUUM INTO backups/netamipin.before-vN.db` | Миграция не начинается, база не тронута | «Не удалось создать резервную копию перед обновлением библиотеки: <причина>. Данные не изменены.» Кнопки «Повторить», «Открыть папку», «Выйти» |
| Одна транзакция: DDL, перенос данных, `user_version = N` | `ROLLBACK`, база остаётся vN−1 | «Не удалось обновить библиотеку. Данные не изменены.» Кнопки «Открыть папку с копией», «Скопировать отчёт», «Выйти». Приложение не работает с базой до исправления |
| После commit — `quick_check` | Копия до миграции уже есть | Плашка о повреждении с восстановлением из `before-vN` |

Автоматического отката на старую схему нет: ошибку в выпущенной миграции исправляет следующая версия. Ручной откат — закрыть приложение, установить предыдущую версию и подставить `before-vN`; изменения после миграции при этом теряются, инструкция поддержки говорит об этом прямо.

**Тестовые библиотеки.** Генератор `src-tauri/examples/test_libraries.rs` строит базы настоящим кодом схемы в `.test-data/libraries` (вне репозитория): пустая v1, старые v0 и v1 со смешанными форматами времени и кириллицей, 10 000 и 100 000 записей, близкие дубликаты адресов, повреждённые страницы, файл не SQLite и папка OddClicks для `NETAMIPIN_LEGACY_DIR`. `scripts/open-test-libraries.mjs` открывает каждую собранным приложением и записывает результат. Генератор детерминирован: одинаковые базы на любой машине.

**Последствия:** NP-006 сначала добавляет проверки открытия, копии и экран ошибок, затем миграцию v2. Расширение отправляет `source` и понимает `restored` (NP-016). Протокол HTTP остаётся `protocol: 1`.

**Проверка:** каждая тестовая библиотека открывается текущей версией или даёт описанную ошибку; миграция v2 проверяется на всех библиотеках генератора, включая отказ записи посреди миграции и повторный запуск.

**Повод пересмотреть:** синхронизации понадобятся надгробия с содержимым; размер копий станет заметен пользователям; импорт браузеров получит вложенные коллекции.
## Р-11. Чистая схема 1 вместо переноса данных

3 октября 2026 года. Задача NP-006. Выбор владельца: пользователей, кроме владельца, нет, поэтому переносить данные не нужно; судьба старой библиотеки, OddClicks и номер схемы — его ответы. Мигратор предложил владелец.

**Контекст:** [Р-10](#р-10-модель-данных-и-миграции) описывал миграцию v2, которая переводит каждую существующую библиотеку: пересоздание таблиц, `uid` из `created_at`, перевод форматов времени, перенос OddClicks. Это самая рискованная и дорогая часть NP-006, а переносить нечего: публичных выпусков не было.

**Решение:**

1. **Схема 1 — сразу целевая модель Р-10:** `uid`, `source`, `triaged_at`, `deleted_at`, `tombstones`, время UTC с миллисекундами, `application_id = 0x4E50494E`. Начальные коллекции и токен создаются в том же шаге, один раз.
2. **Библиотека сборок до схемы 1** (нет `application_id`, есть таблица `bookmarks`) переименовывается вместе с `-wal` и `-shm` в `netamipin.old-<дата-время>.db` рядом, создаётся новая; интерфейс один раз сообщает путь. Файл не удаляется: закладки можно вернуть экспортом HTML из старой сборки и импортом.
3. **OddClicks:** копирование библиотеки и localStorage, чтение ключей `oddclicks.*`, поле `"app":"OddClicks"` в `/api/health` и удаление старого alarm в расширении убраны. Осталось только предупреждение о том, что порт 28765 держит запущенная OddClicks.
4. **Мигратор — [rusqlite_migration](https://crates.io/crates/rusqlite_migration) 1.3** вместо своего цикла. Он хранит номер схемы в `user_version` (как и было), применяет все ожидающие шаги и новый `user_version` в **одной** транзакции и умеет `validate()` для тестов. Линия 1.3 — последняя на rusqlite 0.32; 2.x требует обновить rusqlite. Своё осталось только то, чего в нём нет: проверка файла только для чтения до любой записи, копия `before-vN`, коды ошибок для экрана.
5. **Порядок фоновой проверки** уточняет Р-10, п. 10: сначала `quick_check`, потом копия. Иначе повреждённая библиотека попала бы в копии и вытеснила бы исправные при ротации.

**Варианты мигратора:**

1. rusqlite_migration — выбран: для rusqlite, `user_version`, без лишней таблицы, шаги на SQL и на Rust (`up_with_hook`).
2. refinery — поддерживает rusqlite, но ведёт свою таблицу истории и рассчитан на файлы миграций; `user_version` пришлось бы проверять отдельно.
3. Миграции sqlx или diesel — требуют другого драйвера базы, что противоречит единому пути доступа через rusqlite ([Р-2](#р-2-sqlite-остаётся-единственным-хранилищем)).

**Последствия:** «одна транзакция на все ожидающие шаги» заменяет «каждая миграция в своей транзакции» из [Р-3](#р-3-надёжность-хранилища): при сбое библиотека остаётся на исходной версии целиком, копия `before-vN` делается один раз — перед переходом на последнюю схему. Шаг, пересоздающий таблицу, сам отключает внешние ключи до транзакции. Следующее изменение схемы — шаг 2; выпущенный шаг не меняется.

**Проверка:** Rust-тесты: новая библиотека, повторный запуск, отказ записи (`max_page_count`) и ошибка посреди следующей миграции с откатом и копией, более новая и чужая схема без изменения файла, перенос старой библиотеки, повреждение. Нативные тесты: экран более новой схемы, перенос старой библиотеки, плашка повреждения, повтор после ошибки.

**Повод пересмотреть:** первый публичный выпуск — с этого момента данные пользователей переносятся только миграциями.

## Р-12. TypeScript-типы IPC из Rust: ts-rs

3 октября 2026 года. Задача NP-007. Предложено исполнителем, принимается ревью владельцем.

**Контекст:** команд станет втрое больше, а типы `src/types.ts` и демо-адаптер писались вручную и уже разошлись с Rust: в демо не было `image_url`, `favicon_url`, `count`, ошибки были строками.

**Варианты:**

1. **ts-rs 12** — выбран. Стабильная линия, `#[derive(TS)]` рядом с `Serialize`, понимает атрибуты serde (теги, `rename_all`, адъяцентные перечисления). Файлы пишутся в `src/bindings` во время `cargo test`, поэтому проверка в CI — `git diff` после тестов. Генерирует только типы: имена аргументов команд в `services/api.ts` остаются ручными.
2. **tauri-specta** — генерирует ещё и обёртки команд с именами аргументов и события, то есть закрывает и остаток варианта 1. Но и он, и `specta` на 3 октября 2026 года — `2.0.0-rc.25`, генератор TypeScript — `0.0.12`; экспорт идёт при запуске приложения, а не в тестах. Для контракта, который будет расти, это нестабильная основа.
3. Ручные типы с тестом сверки — не ловят расхождение в момент изменения Rust.

**Решение и причина:** ts-rs — стабилен и проверяется простым способом в CI. Ошибки команд — `CommandError { code, message }`: `code` из закрытого перечисления `ErrorCode` (`invalid_request`, `not_found`, `conflict`, `database_busy`, `disk_full`, `read_only`, `database_error`, `internal`), как `code` в HTTP v1. HTTP v1 не меняется.

**Последствия:** структура, которая пересекает IPC, получает `#[derive(TS)] #[ts(export)]`; `i64` экспортируется как `number` (`TS_RS_LARGE_INT` в `.cargo/config.toml`). Сгенерированные файлы хранятся в git и не правятся руками. Имя аргумента команды по-прежнему может разойтись — это ловят нативные тесты.

**Проверка:** переименование поля `Tag.name` в Rust дало изменение `src/bindings/Tag.ts` (`npm run check:bindings` и шаг CI падают) и ошибки `tsc` в `App.tsx`.

**Повод пересмотреть:** стабильный выпуск tauri-specta 2 — тогда сравнить снова ради типизированных имён команд и событий.
